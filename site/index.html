01

Why a broker exists

Coding agents often need a small amount of trusted context from earlier work. Passing whole transcripts between tools creates privacy, size, and provenance problems.

The broker carries forward bounded facts and short-lived work state, keeps provider histories private, and makes provenance, freshness, and verification state visible to the agent that asks.

02

What crosses the boundary, and what never does

Shared as structured context

  • bounded facts and derived claims with source hashes
  • short-lived work state for related in-flight tasks
  • provider, provenance, freshness, and verification state
  • metadata-only audit records with hashes, counts, warnings, and dispositions

Never passed to another agent

  • raw prompts and responses
  • tool arguments and tool results
  • native session, record, and source identifiers
  • credentials and secret-like values rejected by content safety

Adapters are read-only. They never modify, archive, or delete native histories.

03

How context moves between providers

Adapters are thin bridges. Either provider can be the source or the consumer, and the same core applies the same checks.

  1. Inventory or proposeAn adapter inventories bounded metadata or submits a structured proposal.
  2. ValidateThe core checks paths, schemas, source attestation, content safety, freshness, and expected state.
  3. ReconcileA claim becomes accepted context, stays pending, or is rejected with a reason.
  4. RouteA query returns the smallest matching accepted context and labels peer progress separately.
  5. AuditMetadata-only records capture hashes, counts, and dispositions without conversation content.

Availability fails open. An unavailable broker does not block the agent. Integrity fails closed. Invalid data is never imported or promoted.

04

Two kinds of context, kept apart

Accepted means a claim passed reconciliation and integrity checks. It does not mean the claim is guaranteed to be factually true.

Accepted context compared with live peer progress
PropertyAccepted contextLive peer progress
PurposeDurable facts another agent can build onCoordination hints while related work is in flight
Entry pathStructured candidate claim reconciled against the current snapshotImmutable progress publication from a task
ChecksSchema, content safety, evidence, freshness, expected state, and hashesSchema and content safety; never reconciled

05

Trust boundaries you can inspect

Local-first
The broker runs as local Bun scripts with no hosted component. Runtime state stays in a private per-user directory.
Strict isolation
AGENT_CONTEXT_BROKER_STRICT_ISOLATION=1 returns before registry reads or audit writes.
Provenance
Claims carry source hashes. Accepted snapshots are content-addressed and hashes are checked again on read.
Metadata-only audit
Audit records contain hashes, counts, watermarks, warnings, and dispositions, never prompts or responses.

06

Guarded installation

Installation is plan-only by default. Activation proceeds only when the exact manifest and plan digests are passed back to the unchanged command.

The installer preserves existing lifecycle handlers, creates byte-exact backups, and supports plan-bound removal and rollback.

Full install, verify, remove, and rollback flow 
bun scripts/manage-agent-context-broker-installation.mjs install \
  --provider both > install-plan.json

bun scripts/manage-agent-context-broker-installation.mjs install \
  --provider both \
  --expected-manifest-digest <manifestDigest> \
  --expected-plan-digest <planDigest> \
  --execute
